**Lectic project review — 25 September 2026**

Reviewed revision: `c2b1c690f5a01481f3d4418c7f1a5f8d1eb40a94`, package version `0.3.0`.

**Verdict: Lectic has a credible foundation for substantial value, but it has not yet demonstrated undeniable value or achieved minimal friction.** Its best work is the durable connection between trusted sources, reusable methods, and actual outcomes. Its greatest current weakness is that the public promises and newer distribution features have advanced ahead of reliability and evidence from users.

I would continue the project, narrow the next release around one complete recurring workflow, and pause broader marketplace promotion until the defects below are resolved. A new user should be able to get a useful result, return in a fresh session, and see a correction persist. That experience should determine the roadmap.

| Question | Assessment |
| --- | --- |
| Is the underlying problem worth solving? | Yes: repeatedly turning trusted guidance into useful work is a credible need. Its frequency and willingness to pay remain to be established with users. |
| Is there a meaningful product here? | Yes. Evidence, preserved disagreements, versioned knowledge, and reusable methods form a coherent system. |
| Is superiority over ordinary assistant use established? | No. The reviewed material contains evaluation machinery and a thoughtful study protocol, but no demonstrated live comparative advantage. |
| Is onboarding close? | Local assistant setup is promising. The whole journey from installation to a useful result still has gaps. |
| Is usage friction minimal? | No. Mandatory filing questions, acquisition limits, inconsistent defaults, and silent failures add avoidable work. |
| Is it ready for broad promotion as currently described? | No. Several reproduced defects undermine the advertised reliability and trust guarantees. A focused alpha remains appropriate. |

This is not a claim of exhaustive line-by-line verification or a formal security audit.

The [published release](https://pypi.org/project/lectic/0.3.0/) was available during review. Live network findings are observations from this date. There was no live YouTube acquisition test, phone-device test, paid hosting deployment, independent assistant comparison, or user study in this review. Cross-platform CI is configured, but the suite was executed here on Windows only. No product implementation was changed. [Recorded probe results](D:/Projects/lectic/docs/reviews/2026-09-25-evidence.json) accompany this report.

**What is good: the central asset is useful and well conceived.** Lectic preserves more than a collection of excerpts. Its knowledge units distinguish explicit statements, inference, and synthesis; retain applicability and attribution; and express prerequisites and disagreements. A method can be built from selected knowledge without destroying the original collection. That is a defensible basis for consistent work across multiple tasks, particularly when the source material contains procedures, criteria, and exceptions. [Extraction contract](D:/Projects/lectic/prompts/extract.md:9), [reconciliation contract](D:/Projects/lectic/prompts/reconcile.md:3).

Several choices deserve preservation:

- **Results come before exports.** Reviews, decisions, revisions, plans, and lessons can be delivered directly. Users need not understand skill packaging to receive value. The general outcome contracts enforce useful minimum structure while acknowledging that structure alone cannot establish quality. [Outcome implementation](D:/Projects/lectic/scripts/outcomes.py:1).
- **Reuse is represented explicitly.** Source snapshots, knowledge revisions, historical builds, hashes, and scoped evidence make earlier work inspectable. Tests exercise fresh-process reuse, changed sources, dependency invalidation, interrupted work, and historical validation. These are valuable foundations for long-term trust.
- **Saving is separate from understanding.** Capture can retain a link and the user's reason without pretending the content has been retrieved or interpreted. Retrieval failures and unsupported formats have distinct states. Caption caching and source-local reuse can reduce repeated acquisition and extraction. [Capture processing](D:/Projects/lectic/scripts/capture_store.py:288).
- **Discovery addresses a real usability problem.** Capability Maps and next-use guides help someone who knows their material is valuable but cannot name its best application. The implementation checks support types, preserves recorded disagreements, and separates possible builds from completed methods. [Capability Maps](D:/Projects/lectic/scripts/capability_maps.py:39).
- **Local ownership and assistant interoperability are practical strengths.** The dependency-light core, published package, MCP interfaces, backup/restore, and non-destructive transfer reduce dependence on one assistant or service. The installer uses the actual interpreter rather than relying on a command being on PATH.
- **The older quality guidance is unusually candid.** Build validation explicitly reports effectiveness testing as not run. The comparative study allows the baseline to retain notes and methods, counts setup effort, and admits ties or baseline wins. This is the right standard to retain. [Build validation](D:/Projects/lectic/scripts/goal_workflow.py:87), [evaluation protocol](D:/Projects/lectic/docs/EVALUATION.md:9).

These strengths make the project worth continuing. They do not yet prove that a normal user gets a better outcome for less total effort.

**What is bad: several shipped paths report more success than they deliver.** The following are concrete findings, ordered by the urgency of restoring trust. “P1” means resolve before wider promotion of the affected flow; it does not mean that every user encounters the problem on every request.

**P1 — A pack update can report new knowledge while retaining the old interpretation.** I installed version 1 of a pack, changed a knowledge statement while leaving its original sources unchanged, built version 2, and updated the recipient. The response reported version 2, `verified`, and `knowledge_matches_pack: true`. Reading the recipient's active IR still returned the old statement.

The cause crosses two modules: pack installation validates the staged IR, while collection adoption reuses an existing destination when the source corpus matches. The staged knowledge revision is then discarded rather than activated. The reported hash comparison describes the staging area, not the persisted result. This directly blocks the promise that revised expertise improves future work. [Pack adoption and report](D:/Projects/lectic/scripts/packs.py:388), [existing source revision handling](D:/Projects/lectic/scripts/collection_store.py:97).

**Required outcome:** updates with unchanged sources must retain and activate the incoming knowledge revision, preserve earlier history, and verify the actual saved destination before declaring success. A fresh process must use the corrected statement. Also make version-pin semantics explicit: the current update operation advances a pinned installation without a separate unpin action.

**P1 — Shared storage can lose a saved collection from its index.** I created two `Library` instances before either wrote, then saved a different collection through each. Both collection directories existed afterward, but the library listed only the second. `Library.save` writes its previously loaded index without reloading it inside a shared transaction. Separate assistant processes can reproduce this stale-writer pattern. The HTTP server's in-process lock does not protect independent stdio or CLI processes. [Index write](D:/Projects/lectic/scripts/collection_store.py:42).

**Required outcome:** serialize the complete read-modify-write operation for shared indexes, or use revision-checked updates with conflict handling. Test overlapping clients and recover orphaned collections. Atomic file replacement alone does not solve a lost update. The existing storage transaction primitive provides a starting point.

**P1 — Publisher identity is not verified as advertised, and the signing secret is readable through MCP.** Recipient inspection only checks for a publisher block and returns `signed`; it does not verify the HMAC. Replacing the signature with zeros retained that status. Changing the claimed publisher's name and contact also passed the author's own verification because the signed content excludes the entire publisher block. In a temporary home, `lectic_read` could return `identity.json`, including its secret key. No real credential was accessed or printed during this test. [Signing payload](D:/Projects/lectic/scripts/identity.py:109), [recipient check](D:/Projects/lectic/scripts/identity.py:154), [generic read boundary](D:/Projects/lectic/scripts/lectic_mcp.py:400).

HMAC requires a secret key; a displayed key fingerprint does not enable public verification. This matches the [Python HMAC documentation](https://docs.python.org/3/library/hmac.html). The immediate correction is honest labeling: declared publisher, internally checked contents, author identity unverified. If publicly verifiable signatures are needed, use an established asymmetric implementation with publisher metadata included in the signed payload, trusted-key handling, and key rotation/recovery. [Ed25519 documentation](https://cryptography.io/en/latest/hazmat/primitives/asymmetric/ed25519/) illustrates the private-sign/public-verify model. A valid signature establishes control of a key; binding that key to a named person remains a separate trust decision. Keep signing secrets outside assistant-readable knowledge records.

**P1 — Conversational packing includes full originals by default, even when source inclusion is explicitly false.** The MCP method defaults both `team` and `include_sources` to true. Team mode then forces source inclusion. My call with `include_sources=False` still produced a pack containing sources because `team` remained true. The CLI's ordinary pack default differs. This puts private originals into a distributable artifact when a user may have intended to share only a method and its relevant evidence. No external publication occurred in this review. [MCP defaults](D:/Projects/lectic/scripts/lectic_mcp.py:321), [team override](D:/Projects/lectic/scripts/packs.py:103).

**Required outcome:** use one consistent, explicit sharing scope across interfaces; honor an explicit exclusion; and show what an export contains. Preserve the existing distinction between a scoped method export and a complete knowledge pack. Source attribution alone does not establish redistribution permission.

**P1 — The marketplace's advertised first-use path is currently broken.** All four pack URLs in the registry returned HTTP 404. The live marketplace fetches `../registry/index.json`, which resolves to a missing URL at the GitHub Pages account root; it silently shows its embedded fallback catalog. The page still presents publisher checkmarks, unit counts, and install buttons. Browser “Inspect” displays catalog metadata, not verification of the downloadable pack. CLI inspection also falls back to metadata after download failure. [Registry entries](D:/Projects/lectic/registry/index.json:1), [web fetch](D:/Projects/lectic/docs/registry.html:549), [inspection fallback](D:/Projects/lectic/scripts/registry.py:130).

**Required outcome:** either remove these entries from the available catalog or provide real, tested artifacts. Validate every listed download, manifest, install, and first usable method in release checks. Show unavailable and unverified states explicitly. If the next release uses a starter pack, ship one small, complete, legally shareable example that works offline; a large catalog is unnecessary to demonstrate the value. [Live marketplace](https://tyreamer.github.io/lectic/registry.html).

**P1 — The drop inbox fails in the case where its matching feature should help most.** Candidate matching returns `reasons`, but the scanner reads `reason`. An inbox note matching an existing Debugging collection raised `KeyError: 'reason'`. The library tool catches the exception and omits pending items, making the failure look like an empty inbox. [Scanner](D:/Projects/lectic/scripts/inbox.py:178), [candidate record](D:/Projects/lectic/scripts/candidate_collections.py:214), [suppressed error](D:/Projects/lectic/scripts/lectic_mcp.py:261).

Two related defects were reproduced. Selecting one of two inbox files caused both to be routed because the mapping controls destinations rather than the set of selected files. Injecting an import report with a failure still produced `phase: routed` and moved the original out of the pending folder. The file was retained in `.processed`; this test does not establish permanent deletion. [Routing loop](D:/Projects/lectic/scripts/inbox.py:252), [unchecked import report](D:/Projects/lectic/scripts/inbox.py:230).

**Required outcome:** route only selected items; acknowledge import success for each exact capture before moving its original; preserve failed items as pending with a useful explanation; and surface scan failures. Tests need existing matching collections, multiple pending items, partial selection, and failed imports. Current inbox tests mostly exercise small successful cases without those interactions.

**P2 — Connection status does not prove that an assistant can connect.** Setup is helpful, but `connected` means a configuration entry exists. A temporary Codex entry whose launch command did not exist still reported connected, while the in-process local server check passed. A configured remote server is not verified by checking a different local server. [Configuration check](D:/Projects/lectic/cli.py:101), [server check](D:/Projects/lectic/cli.py:128).

**Required outcome:** distinguish configured, server reachable, and assistant ready. Test the configured command or URL through a real protocol handshake, then offer a simple first-use check after restart. Exercise both supported assistants in fresh sessions before making client-level activation claims. The standalone published-wheel smoke test passed, which is encouraging but narrower evidence.

**What is bad about the product experience, beyond defects.** The interaction contract adds friction at precisely the point where saving should be cheap. Both the skill and MCP guidance require a collection-selection question whenever the user has not named one, even for “save this for later.” An Inbox already exists. Requiring a filing decision before every save turns a useful habit into repeated administration. [Skill instruction](D:/Projects/lectic/SKILL.md:33), [MCP instruction](D:/Projects/lectic/scripts/lectic_mcp.py:39).

My recommendation is to save immediately to Inbox when no destination is supplied, honor explicit destinations, and suggest organization afterward. Ask before an ambiguous merge or consequential move. Let the user opt into remembered routing preferences. A save should leave a clear receipt and an easy correction path.

The “automatically notices my drops” claim also needs qualification. Scanning happens when relevant Lectic tools are called, not through a guaranteed hook on every assistant conversation. A host may never call the library tool in an unrelated chat. Either supply a tested activation mechanism or describe the explicit request that checks the inbox.

The input promise is broader than the acquisition implementation. Text/transcript files work; linked retrieval currently supports YouTube English captions. Other article URLs and file types can be saved without becoming usable content. That distinction exists in the detailed documentation but is much less visible in the headline promise. A further reproduced inconsistency: `lectic_work` advertises YouTube URL input, but its goal coordinator converts that URL to a filesystem path and fails. The capture-processing and legacy compiler paths are separate; this is not a finding that all YouTube retrieval is broken. [Input conversion](D:/Projects/lectic/scripts/goal_workflow.py:111), [available linked adapter](D:/Projects/lectic/scripts/linked_sources.py:10).

For first use, show four understandable states: **saved**, **content available**, **ready to apply**, and **needs attention**. Explain unsupported inputs when they arrive, while retaining what was saved. Do not make a blocked YouTube download the only route to experiencing the product.

The remote and phone journeys remain setup-heavy. They require a reachable running server, a connection link, and host configuration. Quick tunnels change address on restart; the laptop must remain available. These are documented constraints, but they make “paste this pack into any assistant and it immediately adopts your standards” an unreliable general promise. Also correct the cloud guide's suggestion that connecting a home client to a hosted server moves caption acquisition onto the client's network: the remote tool still runs on the server. [Cloud guide](D:/Projects/lectic/docs/CLOUD.md:9), [remote capture processing](D:/Projects/lectic/scripts/lectic_mcp.py:289).

**Public presentation currently undermines the careful core.** The live landing page makes absolute claims about hallucinations and cryptographic anchoring that the implementation cannot establish. Its intake demonstration uses hard-coded match percentages and predetermined output. It should be labeled as an illustration or replaced with a recorded, reproducible example from real inputs. A quotation's presence proves where text came from, not that an interpretation is correct. [Live page source](D:/Projects/lectic/docs/index.html:386), [demonstration values](D:/Projects/lectic/docs/index.html:549).

There are also multiple presentation sources: `docs/index.html`, `docs/launch_site.html`, and the separate React site. The current public URL serves the static Lectic landing page. The React prototype uses the older Expertise Compiler identity and has a waitlist that displays success without storing or submitting the email. This is a latent problem in the secondary site, not a claim that the current public landing page loses signups. The public marketplace also overflowed horizontally at a 390-pixel viewport, with measured document width of 606 pixels. [React waitlist](D:/Projects/lectic/website/src/components/WaitlistSection.tsx:8).

Choose one maintained public site, one primary call to action, and one accurate compatibility/input matrix. Lead with a task and a real output. Technical provenance is supporting evidence for the benefit; it should not require a visitor to understand HMAC, IR, MCP, or package registries before seeing what improves their work.

**The strategic issue is proving compounding usefulness.** The architecture says reusable expertise is the product. Recent messaging makes signed packs and a marketplace the primary differentiation. The north star explicitly prioritizes correction propagation and cautions against marketplace expansion; the release has moved in the opposite direction. This is an unresolved strategy choice, not merely stale wording. [North star](D:/Projects/lectic/NORTH_STAR.md:155), [guardrail](D:/Projects/lectic/NORTH_STAR.md:173).

Packs are useful distribution infrastructure. A file format, hashes, and a catalog do not themselves establish better judgment or meaningful effort savings. The core opportunity is that an expert's conditions, exceptions, and disagreements survive repeated application, and that correcting a mistake improves later outputs. A user should be able to say “this keeps applying our method correctly, and I no longer have to reconstruct it.”

The missing proof is not another synthetic example. It is a fair comparison over initial use, reuse, and an update. The existing [testing guide](D:/Projects/lectic/docs/testing-guide.md:157) is strong enough to execute. I found no completed participant-level evidence in the reviewed material establishing retention, savings, or willingness to pay. Such evidence may exist outside the repository; this review does not assume that it does not exist anywhere.

**The best path forward is a reliability release followed by a focused value trial.** I recommend the following sequence. The time windows are planning suggestions, not delivery estimates based on a known team capacity.

| Sequence | Work | Exit condition |
| --- | --- | --- |
| Immediate: restore trust | Correct public verification and compatibility claims; withdraw broken catalog entries; fix pack updates, shared-index writes, source-export defaults, secret-read boundaries, and inbox routing. | Every reproduced failure has a regression test or the affected promise/flow is removed. Success responses describe persisted state. |
| Next development cycle: finish one first-use journey | Assistant-led setup, restart, an offline starter example, first meaningful result, one clear next-use prompt, and fresh-session reuse. Correct direct URL routing and connection diagnosis. | An ordinary user completes the journey without commands, JSON, manual transcript preparation, or developer repair. |
| Following 2–4 weeks: run the existing pilot | Execute the 10–14-person, two-wave study; separate guided cases from independent attempts. Focus the main message on one recurring job and retain comparison cases from other domains. | Publish raw completion counts, paired outcomes, active effort, failure reasons, and voluntary return behavior. |
| Then: strengthen persistent quality | Implement a small correction record bound to a unit/source revision, affected-method tracking, and a regression case. Preserve the prior interpretation and distinguish a user override from a source claim. | A correction survives fresh sessions and new builds; changed evidence triggers reconsideration; old builds remain inspectable. |
| Expand only after the benefit is observed | Add the next ingestion adapter, hosted convenience, or distribution feature that removes the largest measured barrier. | The decision names the observed user failure or repeated request it resolves. |

For the first marketed workflow, I would test **recurring review of real work against user-owned guidance**: an AI builder or consultant brings a small set of standards or training transcripts, gets a source-backed review, and uses the same method again the following week. It fits the shipped text outcomes, offers concrete quality checks, and avoids depending on a large public content catalog. This is a hypothesis to test, not a reason to hard-code the compiler around one profession.

A clear first-use promise would be: **“Save guidance you trust. Use it to review your work, with reasons you can trace. Keep the method for next time.”** The first session should show a tangible before/after result and a source passage that changed the recommendation. The second session should demonstrate why keeping the method mattered.

Keep the internal pipeline and rigorous validation, but progressively reveal complexity. Users should usually need only to save material, request work, inspect a source when useful, and correct an interpretation. Discovery is valuable for a goal-free user; it should not become a mandatory stop before a known task. Signing identity and publishing setup belong at the point of sharing, rather than in every user's initial value path.

**Define success before running the trial.** The existing guide already proposes sensible gates. Retain those, show counts alongside percentages, and treat a small pilot as directional evidence rather than population-wide proof.

| Gate | Recommended decision rule |
| --- | --- |
| First useful result | At least 80% of the less-assisted wave succeed without facilitator repair. Count failed setup and unavailable content in the denominator. |
| Source fidelity and preservation | No unresolved critical misrepresentation in delivered work, no loss of accepted captures/history, and no misleading success state. |
| Comparative value | At least 60% show a predeclared paired value win across initial use, reuse, and update. Comparable quality with worthwhile total effort savings is a valid win. |
| Fresh-session reuse | At least 80% succeed without resupplying sources. Check the actual reopened knowledge revision. |
| Voluntary return | At least half initiate another real use outside the required study tasks. |
| Friction diagnostics | Record user questions, clarification turns, active minutes, assistant elapsed time, repairs, tool retries, and acquisition failures. Establish latency targets from the observed workflow. |
| Correction transfer | Test one corrected interpretation on an unseen task and check that previously correct behavior remains intact. |

Use equivalent models, sources, tasks, persistent-context access, and correction budgets in both arms. Include compilation/setup cost. Keep the independent baseline separate from any session that has seen the compiled method. Do not treat the number of sources, packs, knowledge units, or passing schema checks as the primary value metric. [Study gates](D:/Projects/lectic/docs/testing-guide.md:242).

Measure larger collections before making scale claims. The library view revalidates saved sources/builds and candidate matching reads collection profiles; capture reuse searches historical revisions. These operations are sensible at small scale, but realistic latency and assistant context cost were not established here. The MCP tool catalog alone serializes to roughly 20 KB. That is a reason to measure total interaction cost, not evidence that the protocol is inherently too large. Cache or batch only where measurements justify it.

**Work to defer.** Broader marketplace acquisition, additional presentation sites, multiple new artifact runtimes, persona features, a graph database, and a major core rewrite should wait. The current 7,618 lines of non-test Python are small enough to repair incrementally. Strengthen transaction boundaries and cross-module contracts before adding more surfaces. Keep one release version visible in diagnostics alongside separately named schema/protocol versions, and choose a clear supported update channel rather than asking users to reconcile PyPI installs with skills that follow `main`.

The decision after the pilot should be explicit: continue narrowly if repeat value appears; repair onboarding if useful outcomes are inaccessible; focus on a particular recurring job if benefits concentrate there; reconsider the premise if a capable ordinary assistant matches both quality and total effort and people do not return. More features would not resolve that last result.

**My recommendation is to keep building Lectic, with the next milestone defined as a trustworthy second use.** The project has enough architecture and feature breadth to test its central claim now. Make the current promises accurate, close the reproduced reliability gaps, and demonstrate that saved expertise produces repeated useful work with less user effort. That would give the project a much stronger basis for expansion than another release centered on distribution features.
